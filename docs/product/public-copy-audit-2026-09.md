# Rebase 官网固定文案对外信息审阅

审阅日期：2026-09-08

## 1. 审阅目的

Rebase 官网的首要任务，是向不了解 Rebase 的人介绍这个社区，让访客知道：

1. Rebase 是谁。
2. Rebase 为什么存在。
3. Rebase 长期在做什么。
4. 哪些人正在参与。
5. 访客可以从哪里获取信息、参加活动、发现机会或加入协作。

本轮只围绕这个任务审阅固定文本。判断标准不是“这一块页面叫什么”，也不是“这一块功能如何实现”，而是：**这句话有没有在提供 Rebase 的真实信息；如果没有，它是否应该被换成更有信息量的介绍。**

审阅范围包括首页、About、GeekDaily、文章、活动、招聘、贡献者、页头页脚、二维码提示、404/空状态/错误提示和 RSS 名称。岗位、文章、活动和贡献者的动态资料也做了对外可读性检查。

## 2. 总体结论

### 2.1 官网目前更像“内容栏目目录”，不像 Rebase 的介绍页

首页主要告诉用户“这里有日报、文章、招聘和活动”，但没有先讲清楚这些内容为什么属于 Rebase、它们共同服务什么目标。访客可以看到很多入口，却不容易形成一句完整的认识：

> Rebase 是一个由开发者共同维护的社区，通过内容整理、活动组织和公开协作，让技术信息、机会和人与人之间的连接持续发生。

这句话所包含的四层信息——身份、目标、长期工作、参与方式——应成为全站固定文案的主线。

### 2.2 许多固定文本是在解释“栏目如何运转”，不是在介绍“Rebase 做了什么”

当前文案大量出现以下表达：

- “最稳定的社区更新机制”
- “把内容组织成可搜索、可订阅的长期档案”
- “社区志愿者会做基础格式整理”
- “固定路径”“链接规范”“检索数据”
- “内容密度”“主稿入口”“接引人”

这些话站在维护者角度解释栏目机制，却没有回答用户更关心的内容：Rebase 关注哪些事情、这些栏目为社区带来什么、我为什么要继续了解。

### 2.3 About 才是介绍 Rebase 的核心页面，但目前没有稳定地承担这个任务

About 的默认标题仍是首页定位语的重复版本；内容缺失时显示“内容正在整理中”，会让外部访客感觉社区尚未准备好介绍自己。About 应成为全站唯一完整讲述 Rebase 的地方，首页只保留简短摘要并引导进入 About。

### 2.4 栏目之间缺少共同的 Rebase 叙事

GeekDaily、文章、活动、招聘和贡献者页面各自说明“这里有什么”，但没有说明它们共同构成了 Rebase 的哪些工作：

- GeekDaily：持续整理技术信息和行业信号。
- 文章：保留社区成员的经验、判断和复盘。
- 活动：让开发者围绕技术与实践见面交流。
- 招聘：连接社区里的工作机会和人才。
- 贡献者：说明这些内容、活动和工具由谁共同维护。

这些关系需要在各页面固定摘要中直接说出来。

### 2.5 对外信息应减少口号和内部术语，增加事实、范围和参与方式

“用热爱”“真实的人”“持续往前推”“内容密度”等表达不能帮助访客判断 Rebase 是什么。对外文案应优先使用可验证的事实和具体动作；“非营利”“公益”“中国开发者”等身份表述则应由社区负责人确认后统一使用，不能在不同页面自由变化。

## 3. Rebase 官网应该稳定传达的五类信息

| 信息 | 官网应该回答 | 当前缺口 |
| --- | --- | --- |
| 身份 | Rebase 是什么社区 | 首页只有长定位语，没有简短、稳定的定义 |
| 目标 | 为什么做这些栏目和项目 | 各栏目只讲功能，不讲它们对社区的意义 |
| 工作 | Rebase 长期做什么 | “组织内容、活动、招聘和协作”没有被组织成一段完整叙述 |
| 参与者 | 谁在让社区持续发生 | 贡献者页偏重角色和内部联系人，缺少共同维护的说明 |
| 参与入口 | 外部读者怎样阅读、参加、投稿或协作 | 入口存在，但分散且有内部称呼，About 没有总览 |

## 4. 全站固定文案审阅

### 4.1 页头与导航：先让访客知道去哪了解 Rebase

当前导航为：`首页｜极客日报｜Who-Is-Hiring｜文章｜活动｜贡献者们｜关于Rebase`。

存在的问题：

- `Who-Is-Hiring` 对第一次访问者不是自然的中文栏目名。
- `贡献者们`、`关于Rebase` 排版和其他栏目不一致。
- 导航没有一个清晰的 `关于 Rebase` 入口形象，访客不容易知道去哪里了解社区背景。

建议统一为：

`首页｜关于 Rebase｜极客日报｜文章｜活动｜招聘｜贡献者`

如果团队希望保持当前顺序，也至少将名称统一为：

`首页｜极客日报｜招聘｜文章｜活动｜贡献者｜关于 Rebase`

`Who-Is-Hiring` 只在项目仓库或正式项目名称中保留；面向用户的栏目标题使用“招聘”。

### 4.2 首页：从“栏目列表”改成“Rebase 介绍 + 栏目证明”

#### 当前首屏

- `建设面向开发者和创新者的社区`
- `Rebase Community 是由中国开发者们在业余时间用热爱建立的开发者社区。`
- `这是一个由中国开发者用热爱和业余时间共同维护的非营利、公益性开发者社区。`
- `进入 GeekDaily`
- `查看招聘板`

#### 问题

这些话重复描述创建者和情感，却没有说清楚 Rebase 提供什么价值；“创新者”“招聘板”也不是所有访客都能立即理解的词。

#### 建议首屏成稿

- 眉题：`一个持续发生的开发者社区`
- 标题：`Rebase 连接技术信息、社区协作和真实的人。`
- 摘要：`我们通过 GeekDaily、文章、活动、招聘和开源协作，记录行业变化、分享实践经验，也为愿意一起做事的人提供公开入口。`
- 主按钮：`了解 Rebase`
- 次按钮：`浏览最新内容`

“非营利”“公益”“中国开发者”“业余时间”等信息可以放进 About 的“我们是谁”，不要在首页首屏重复三次。最终身份表述由负责人确认。

#### 首页各区块

| 当前固定文案 | 对外信息问题 | 建议改写 |
| --- | --- | --- |
| `社区正在发生什么` | 只说明有动态，没有说明这些动态属于 Rebase 的哪类工作 | `Rebase 最近在做什么` |
| `日报是最稳定的社区更新机制，紧随时代变化，也是搜索与RSS最常用的入口` | 站在运营角度比较栏目，无法说明 GeekDaily 对社区的作用 | `GeekDaily 持续整理值得关注的技术内容和行业信号。` |
| `从产品、社区、新技术、新探索到信息架构，公开记录社区内的想法` | 主题罗列过宽，未说明内容来自谁、为什么公开 | `记录社区成员的实践、判断和复盘，让有价值的经验可以被长期阅读。` |
| `由招聘方在社区github上提交的招聘信息，社区志愿者只做最简单的格式筛选，大家需要认真辨别` | 把流程细节和风险提醒混在一起，语气像内部公告 | `汇总社区收到的公开岗位，帮助开发者发现工作机会；岗位由招聘方提交，投递前请自行核实。` |
| `由 Rebase 主办和参与合作的活动，以及在github上提交的活动都将展示在这里` | 讲提交来源，没有说明活动与社区的关系 | `通过线上和线下活动，让开发者围绕技术、产品与社区实践交流。` |
| `由更多真实的人，一起把社区持续往前推` | 情绪表达，无法说明贡献者是谁 | `认识让 Rebase 持续发生的人` |
| `先看见真实的人，再进入完整的贡献者档案` | “真实的人”是口号，未说明贡献内容 | `志愿者、编辑和长期协作者共同维护 Rebase。` |
| `内容整理、活动组织、推荐协作与长期共建，都会慢慢沉淀成可被看见的记录` | “慢慢”“可被看见”抽象 | `内容、活动和协作记录会持续公开，成为 Rebase 的社区档案。` |
| `通过 RSS 持续追踪 Rebase 的公开内容更新` | 只讲工具，不讲订阅内容是什么 | `订阅 RSS，持续接收 Rebase 的日报、文章、活动和招聘更新。` |

### 4.3 About：从占位页改成 Rebase 的完整自我介绍

#### 当前问题

- 默认标题重复首页长句，不适合作为“关于我们”的标题。
- 空状态写“我们会很快补充”，给出无法兑现的时间承诺。
- 栏目、渠道、联系方式和捐赠地址堆在一起，缺少“为什么存在”的主线。

#### 建议固定成稿

标题：`关于 Rebase`

摘要：

`Rebase 是一个由开发者共同维护的非营利社区。我们通过内容整理、活动组织和公开协作，让技术信息更容易被发现，也让愿意一起做事的人更容易找到彼此。`

建议正文分为四段：

**我们是谁**

`Rebase 由关心技术、产品和开放协作的开发者共同维护。我们不只发布信息，也努力把有价值的内容、机会和社区经验保留下来，成为可以被持续访问的公共记录。`

**我们在做什么**

`GeekDaily（极客日报）整理技术文章、工具、研究和行业信号；文章栏目记录社区成员的经验、判断和复盘；活动栏目连接线上线下交流；招聘栏目汇总社区中的公开岗位；协作项目则让更多人可以参与内容、工具和社区维护。`

**如何参与**

`你可以阅读和订阅公开内容，推荐一篇值得分享的文章，提交岗位或活动，也可以从一次具体协作开始参与社区维护。先从自己最熟悉的一件事开始即可。`

**联系与支持**

按“内容、活动、协作、社交、捐赠”分组展示入口。捐赠部分必须写清资金用途、网络名称、地址核验方式和风险提示；在信息确认前，不使用没有依据的号召性语句。

空状态建议改为：

`关于 Rebase 的介绍正在准备中。你可以先浏览 GeekDaily、文章、活动和贡献者页面。`

如果页面短期内无法提供完整介绍，至少应保留上面的摘要和栏目入口，不要只显示“内容正在整理中”。

### 4.4 GeekDaily：说明它是 Rebase 的内容工作，而不是说明归档机制

#### 当前固定文案

- `Rebase 极客日报`
- `极客日报是 Rebase 最稳定的持续发声机制。每天更新的极客日报，把社区推荐、工具、研究和信号组织成可搜索、可订阅的长期档案。`
- `由社区志愿者持续整理发布，每期收录值得关注的技术内容、推荐人和推荐语，方便你按期回看、检索与订阅。`

#### 问题

“最稳定的持续发声机制”“可搜索、可订阅的长期档案”是维护者描述；“每天更新”是未经确认的承诺。访客更需要知道日报关注什么、由谁维护、对自己有什么帮助。

#### 建议成稿

标题：`GeekDaily（极客日报）`

摘要：

`GeekDaily 是 Rebase 持续更新的技术内容栏目。社区志愿者会整理文章、工具、研究和行业信号，并附上推荐人和推荐理由，方便你按期了解 Rebase 关注过什么。`

搜索框：`搜索期号、标题、推荐语或推荐人`

详情页侧栏：

- `本期内容`，不要使用 `链接规范`。
- `继续浏览`，不要使用 `继续追踪`。
- `详情页保留本期推荐，方便你从搜索或订阅再次回看。`

只有在确实能够保证每日发布时，才使用“每天更新”；否则统一使用“持续更新”。

### 4.5 文章：介绍 Rebase 如何保留经验和判断

#### 当前固定文案

`把社区里的想法、复盘和方法整理成可以继续阅读的文章。欢迎推荐好内容，也欢迎把自己的文章投递给社区志愿者整理发布。`

#### 问题

“可以继续阅读”是结果描述，不是 Rebase 的内容定位；“社区志愿者整理发布”也不如“保留谁的经验、服务什么阅读需求”重要。

#### 建议成稿

标题：`Rebase 文章`

摘要：

`这里记录社区成员的实践、判断和复盘，保留值得长期阅读的经验。你可以推荐文章，也可以把自己的内容分享给社区。`

空状态：

`目前还没有更多公开文章。新的内容会继续记录社区正在经历和思考的事情。`

详情页的 `Longform Dispatch` 改为 `社区文章` 或移除；它不能帮助用户理解 Rebase。

### 4.6 活动：说明 Rebase 通过什么方式让人见面

#### 当前固定文案

`这里展示 Rebase 社区主办、参与和协助传播的活动。你可以查看近期活动，也可以回看历史活动归档。`

#### 问题

“主办、参与和协助传播”是组织者视角，读者不知道参加活动能获得什么，也不知道 Rebase 的活动主题。

#### 建议成稿

标题：`Rebase 活动`

摘要：

`Rebase 通过线上和线下活动，让开发者围绕技术、产品、开源和社区实践交流。这里汇总近期安排，也保留过去的活动记录。`

按钮与状态：

- `提交活动`：旁边说明 `通过 GitHub Issue 提交公开活动`。
- `立即报名`：有有效报名链接时使用。
- `查看活动详情`：进入本站详情页时使用。
- `正在报名`、`即将举行`、`往期活动`：固定为三种状态。
- `目前没有待发布的公开活动。历史活动见下方归档。`：替换“近期暂无公开活动”。
- `参与方式请查看活动说明；如有变更，以活动方最新公告为准。`：替换“或以后续公告为准”。

活动时间统一补充 `时间均为北京时间（UTC+8）`，避免外地用户误解。

### 4.7 招聘：说明这是 Rebase 提供的连接入口，不是招聘背书

#### 当前固定文案

`Who-Is-Hiring 是 Rebase 的免费招聘频道。团队可以通过 GitHub issue 提交岗位，社区志愿者会做基础格式整理；求职者仍需要自行辨别信息真实性。`

#### 问题

这段话把项目英文名、提交流程、社区工作和风险推给用户，仍然没有说明招聘栏目为什么存在。`提交职位`、`外部投递链接`、`公司未公开`等词也偏内部。

#### 建议成稿

标题：`Rebase 招聘`

摘要：

`这里汇总 Rebase 社区收到的公开岗位，帮助开发者发现工作机会，也帮助团队找到合适的人。岗位由招聘方提交，社区只做基础整理，不对岗位真实性或招聘结果作保证；投递前请自行核实。`

按钮：`提交岗位`、`订阅招聘 RSS`

详情页：

- `公司信息未公开`，替换 `公司未公开`。
- `支持远程`、`需要到岗`、`混合办公`，替换模糊的 `远程`、`线下优先`。
- `前往投递`，替换 `外部投递链接`。
- `该岗位已过期。如仍有兴趣，请先向招聘方确认是否继续开放。`，替换“已由运营标记为过期”。
- `投递方式`、`更多岗位`、`继续浏览`可以保留。

招聘页的免责声明要让用户知道 Rebase 的边界，但不要使用“运营标记”“基础格式筛选”等后台过程词。

### 4.8 贡献者：介绍谁在共同维护 Rebase

#### 当前固定文案

- `贡献者做什么？`
- `参与内容推荐，日报更新，整理招聘信息，组织社区活动，撰写社区内容、维护社区网站和工具，以及 Github 维护`
- `需要什么能力？`
- `有热忱参与开源社区，有兴趣了解最近的行业变化，愿意投入到实实在在的具体的事情上，希望认识更多有趣的人`
- `如何成为贡献者？`
- `任何想要参与贡献的人都可以成为贡献者，在社区中联系接引人 Harry、Frozen、Shooter 或任一名志愿者即可`

#### 问题

页面在描述招募和角色管理，却没有先介绍“Rebase 由谁共同维护”。“接引人”“内容密度”“贡献者会被记录和认可”等说法会让用户猜测社区内部规则，也把固定姓名变成维护负担。

#### 建议成稿

标题：`认识 Rebase 的贡献者`

摘要：

`Rebase 的内容、活动、网站和工具由志愿者、编辑和长期协作者共同维护。每个人从自己熟悉的一件具体事情开始，让社区持续有新的内容和连接。`

三张概览卡：

- `可以参与什么？`：`推荐内容、更新 GeekDaily、整理招聘、组织活动、撰写文章，以及维护网站和工具。`
- `适合怎样的人？`：`关心技术与社区，愿意投入时间完成一件具体协作。`
- `如何开始？`：`从推荐一条内容、参加一次活动或完成一次协作开始，通过公开社区渠道联系我们。`

角色说明：

- 志愿者：`参与内容、活动、工具或日常社区协作。`
- GeekDaily 推荐人：`为 GeekDaily 提供值得关注的内容线索和推荐理由。`

按钮使用 `查看参与方式` 或 `参与日报推荐`，不要使用没有明确结果的 `加入我们`。数量使用 `X 位贡献者`，不要使用 `X 位成员`。

### 4.9 页脚和社交渠道：补充“Rebase 是谁”，不要只堆链接

页脚应保留项目、栏目和社交链接，但顶部摘要应是一句稳定的 Rebase 介绍，而不是机械拼接 tagline。建议：

`Rebase 是由开发者共同维护的社区，持续整理技术内容、活动、岗位和公开协作。`

社区项目链接可以保留官方名称，但建议在链接名称或 About 中补充作用说明，例如：

- `Web3Camp｜开发者学习与交流项目`
- `Rebase Hackathon｜黑客松与项目协作`
- `Web3 极客日报｜技术内容推荐栏目`
- `Event Pool｜社区活动提交与归档`
- `社区福利｜面向社区成员的公开资源`

社交渠道统一为 `B 站`、`YouTube`、`Discord`、`X`、`Telegram`、`GitHub`、`微信公众号`、`QQ 群`。二维码提示保留具体动作：

- `打开微信，扫描二维码关注 Rebase 公众号。`
- `打开 QQ，扫描二维码加入 Rebase QQ 群（群号：1001507060）。`

### 4.10 404、空状态和错误提示：简短说明，不冒充 Rebase 介绍

这些文本不是介绍 Rebase 的主场，越短越好；当前“这页内容暂时没有被找到”“这个招聘页面暂时没有被找到”不自然，也没有提供有用信息。

统一建议：

- 普通页面：`找不到这个页面` / `链接可能已失效，或页面已经移动。` / `回到首页`
- 文章：`暂时找不到这篇文章` / `返回文章列表`
- 活动：`暂时找不到这个活动` / `返回活动列表`
- 岗位：`暂时找不到这个岗位` / `返回招聘列表`
- GeekDaily：`暂时找不到这期 GeekDaily` / `返回 GeekDaily 列表`
- 搜索无结果：`未找到匹配内容` / `换个关键词，或清空筛选条件后重试。`
- 内容暂时不可用：`暂时无法加载内容` / `请稍后刷新，或返回列表继续浏览。`

## 5. 统一对外词汇

| 对外使用 | 替换当前表达 | 原因 |
| --- | --- | --- |
| `关于 Rebase` | `关于Rebase` | 正确的中英文排版，也是访客寻找社区介绍的明确入口 |
| `招聘` | 导航中的 `Who-Is-Hiring`、`招聘板` | 用户一眼知道内容 |
| `GeekDaily（极客日报）` | 首次只写 `GeekDaily` | 让不了解栏目的人知道它是什么 |
| `贡献者` | `贡献者们`、`成员` | 不暗示会员系统，强调共同维护 |
| `持续整理` | 未确认的 `每天更新` | 不制造无法兑现的频率承诺 |
| `社区档案` | `长期档案`、`固定路径` | 说明对用户的价值，而非实现方式 |
| `搜索` | `检索`、`历史检索数据` | 与用户看到的搜索框保持一致 |
| `固定链接` | `链接规范` | 用户可理解 |
| `前往投递` | `外部投递链接` | 直接说明点击后的结果 |
| `继续浏览` | `继续关注`、`继续追踪` | 不虚构收藏、关注或订阅能力 |
| `GitHub` | `github`、`Github` | 品牌名称正确 |
| `X` | `Twitter`、`X / Twitter` 混用 | 渠道名称一致 |

## 7. 落地顺序

### 第一阶段：建立 Rebase 的对外身份

- 确认全站一句话、About 摘要和“非营利/公益/中国开发者”等事实表述。
- 将导航、页脚和页面标题统一为用户能理解的中文栏目名。
- 重写首页首屏，让它先介绍 Rebase，再展示栏目内容。

### 第二阶段：让每个栏目说明自己为什么属于 Rebase

- GeekDaily 说明“持续整理技术内容和行业信号”。
- 文章说明“保留社区成员的经验、判断和复盘”。
- 活动说明“让开发者围绕技术与实践交流”。
- 招聘说明“连接社区里的工作机会和人才，同时不为岗位真实性背书”。
- 贡献者说明“谁在共同维护这些内容和协作”。

### 第三阶段：补齐信任和长期信息

- 重写 About 正文、参与方式、联系方式和捐赠说明。
- 重写活动报名、招聘投递、过期岗位和外部链接提示。
- 统一 404、空状态、错误提示和 RSS 名称。
- 按用户可读规则整理岗位、活动、贡献者和文章的中英文元数据。

## 8. 最终验收问题

文案更新后，任何第一次访问官网的人都应该能回答：

1. Rebase 是什么？
2. Rebase 长期在做什么？
3. GeekDaily、文章、活动和招聘分别和 Rebase 有什么关系？
4. 谁在维护这些内容？
5. 我从哪里可以开始阅读、参加、投稿、找工作或参与协作？
6. 哪些信息是社区提供的，哪些信息需要我自己核实？

如果用户只能说出“这里有很多栏目”，却说不出 Rebase 的身份、工作和参与方式，说明固定文案仍然停留在栏目说明层面，需要继续改写。
