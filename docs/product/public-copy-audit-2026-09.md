# Rebase 官网文案用户视角审阅

审阅日期：2026-09-08
审阅对象：Rebase 面向公众的官网页面、页头页脚、内容卡片、详情页、空状态、错误提示和 RSS 入口
本轮目标：站在访客、读者、求职者、招聘方、活动参与者、贡献者和订阅者的角度，判断文案是否让人“看得懂、信得过、做得到下一步”。

## 1. 本轮审阅方式

这次不从“代码里有哪些字符串”出发，而是模拟用户完成以下任务：

1. 第一次打开网站，想在几秒内知道 Rebase 是什么。
2. 想找一篇值得读的文章或一期 GeekDaily。
3. 想找工作，或想发布一个岗位。
4. 想参加活动，判断是否还能报名。
5. 想了解谁在维护社区，以及自己如何参与。
6. 想订阅更新，不想每天重新打开网站。

每一段文案都用四个问题检查：

- 我现在看到的内容是什么？
- 这和我有什么关系？
- 我下一步可以做什么？
- 这句话是否让我产生错误期待或不必要的不安？

## 2. 从用户角度看到的总体问题

### 2.1 第一次访问仍然不容易理解 Rebase 是什么

首页同时出现“建设面向开发者和创新者的社区”“非营利、公益性开发者社区”“社区正在发生什么”等表达，但没有用一句最简单的话说明：这里能为访客提供哪些内容和行动入口。

用户更需要的是：**这是一个持续整理技术内容、活动、岗位和社区协作的开发者社区。你可以阅读、参加、发布或参与维护。**

### 2.2 文案经常让用户猜内部含义

“主稿”“接引人”“内容密度”“链接规范”“检索数据”“参与合作”等词对维护者可能自然，对第一次来的用户却没有帮助。用户不应该先理解社区内部工作方式，才能找到一篇文章、一个岗位或一次活动。

### 2.3 用户能看到入口，但不总能判断入口会带来什么

“进入 GeekDaily”“查看招聘板”“提交活动”“外部投递链接”等按钮告诉了用户动作，却没有始终说明结果。按钮应让用户知道点击后会看到什么、是否离开本站、是否仍可报名或投递。

### 2.4 信任信息不够集中

招聘页面的真实性提示、活动报名状态、贡献者参与方式、捐赠说明分别散落在不同位置。用户需要在行动前快速确认“谁负责、是否仍有效、出了问题找谁”，这些信息应在相关行动旁边出现，而不是只藏在 About 或长段落中。

### 2.5 文案给出了一些无法由用户验证的承诺

“每天更新”“最稳定”“最常用”“很快补充”等说法会提高期待，也会在实际不符合时损害信任。用户更关心内容是否能持续找到、是否有日期、是否能订阅，而不是宣传式比较。

## 3. 按用户任务审阅

### 3.1 新访客：我想知道这里是什么

| 用户看到的内容 | 用户可能的疑问 | 建议 |
| --- | --- | --- |
| `建设面向开发者和创新者的社区` | “创新者”具体指谁？我能在这里做什么？ | 改为 `面向开发者的社区媒体` |
| `Rebase Community 是由中国开发者们在业余时间用热爱建立的开发者社区。` | 句子很长，重点是身份还是内容？ | 标题直接说价值：`Rebase 是一个持续更新的开发者社区。` |
| `进入 GeekDaily` | 不知道 GeekDaily 是什么，为什么要进入？ | 首次写 `浏览 GeekDaily（极客日报）` |
| `查看招聘板` | “招聘板”像内部看板，不像公开岗位列表 | 改为 `查看招聘` |
| 首页多个区块都解释社区定位 | 用户要读很多介绍才能看到内容 | 首屏只保留一句定位；下面直接展示内容和明确入口 |

首屏建议成稿：

- 眉题：`面向开发者的社区媒体`
- 标题：`Rebase 是一个持续更新的开发者社区。`
- 摘要：`在这里阅读 GeekDaily、文章、活动和招聘信息，也可以通过公开渠道参与社区协作。`
- 主按钮：`浏览 GeekDaily（极客日报）`
- 次按钮：`查看招聘`

### 3.2 内容读者：我想快速找到值得读的内容

| 页面/文案 | 用户感受 | 建议 |
| --- | --- | --- |
| `社区正在发生什么` | 方向正确，但用户不知道下面混合了哪些内容 | 下方保留“文章/招聘/活动/GeekDaily”短标签；无需再加解释 |
| `日报是最稳定的社区更新机制，紧随时代变化，也是搜索与RSS最常用的入口` | “最稳定”“最常用”像没有依据的宣传；`RSS` 缺空格 | `持续更新技术内容与行业信号，支持按期浏览、搜索和 RSS 订阅。` |
| `从产品、社区、新技术、新探索到信息架构，公开记录社区内的想法` | 范围太大，不知道文章适合谁 | `记录社区里的想法、复盘与方法，方便长期阅读和回看。` |
| `Longform Dispatch` | 中文读者不知道这是文章类型 | 改为 `深度文章`，或删除这个装饰标签 |
| `链接规范` | 用户不关心站点如何生成链接 | 改为 `固定链接`；侧栏说明改为 `方便从搜索或订阅再次访问。` |
| `文章标签`、`继续阅读`、`延伸阅读` | 用户可以理解 | 保留，作为详情页稳定用语 |
| `当前先保留主稿入口` | “主稿”是内部编辑词 | 改为 `当前暂无更多文章，新的内容会继续补充到归档中。` |

文章详情页应让标题、摘要、作者、发布时间和正文尽快出现；不要在正文前再放一段社区宣传语。

### 3.3 GeekDaily 读者：我想按期阅读、搜索和订阅

| 当前文案 | 用户问题 | 建议 |
| --- | --- | --- |
| `Rebase极客日报` | 标题挤在一起 | `Rebase 极客日报` |
| `每天更新的极客日报` | 如果有漏更，用户会认为网站失信 | `持续更新的 GeekDaily`；只有能保证每日发布时才写“每天” |
| `搜索期数、标题、推荐语、条目标题或推荐人` | 信息全，但输入框显得复杂 | `搜索期号、标题、推荐语或推荐人` |
| `标签筛选`、`年份筛选`、`清空筛选` | 直白可用 | 保留 |
| `找到 X 期`、`共 X 期` | 用户不确定“期”指什么 | 首次出现写 `共 X 期 GeekDaily`；有筛选时写 `找到 X 期` |
| `没有找到匹配的 GeekDaily` | 句子不完整 | `未找到匹配的 GeekDaily 期目` |
| `你可以尝试换一个关键词，或者先清空年份筛选再继续搜索。` | 给了建议，但不够短 | `换个关键词，或清空筛选条件后重试。` |
| `正在加载历史检索数据...` | “检索”像技术错误 | `正在加载搜索索引...` |
| `检索暂不可用` | 用户不知道还能做什么 | `搜索暂不可用，请稍后重试；你也可以先浏览默认归档。` |
| `归档暂不可用` | 信息不完整 | `归档加载失败，请稍后刷新。` |
| `本期编辑：`、`推荐人：`、`本期推荐`、`期数信息` | 能帮助读者理解内容 | 保留 |
| `链接规范` | 维护者术语 | 改为 `固定链接` |
| `继续追踪` | 不清楚是关注、订阅还是返回 | 改为 `继续浏览`，下面直接放 `订阅 GeekDaily RSS` 和 `回到 GeekDaily 列表` |

GeekDaily 详情页固定结尾建议：`Rebase 极客日报由社区志愿者共同维护，持续整理值得关注的技术内容与行业信号。` 这句话可以保留一次，不要在列表 hero 再重复同一层意思。

### 3.4 求职者：我想判断岗位是否可信、是否还能投递

| 当前文案 | 用户疑问/风险 | 建议 |
| --- | --- | --- |
| `Who-Is-Hiring 是 Rebase 的免费招聘频道。` | 新用户不知道这是岗位列表还是外部项目 | `这里发布 Rebase 社区收到的公开岗位信息。` |
| `社区志愿者会做基础格式整理；求职者仍需要自行辨别信息真实性。` | 责任边界重要，但语气像把风险推给用户 | `岗位由招聘方提交，社区仅做基础格式整理，不对信息真实性或招聘结果负责。投递前请自行核实公司、岗位和联系方式。` |
| `公司未公开` | 是公司不存在，还是招聘方没有填写？ | `公司信息未公开` |
| `远程`、`支持远程`、`线下优先` | 同一信息在卡片和详情页含义不同 | 统一为 `支持远程`、`需要到岗`、`混合办公` |
| `提交职位` | 页面其他位置都说“岗位” | 改为 `提交岗位` |
| `外部投递链接` | 用户不知道会跳到哪里 | 改为 `前往投递`，并在按钮旁标注 `将打开外部页面`（如有空间） |
| `该岗位已由运营标记为过期...` | 用户不关心后台如何标记 | `该岗位已过期。如仍有兴趣，请先向招聘方确认是否继续开放。` |
| `投递方式` | 清楚 | 保留 |
| `继续关注` | 用户不知道是收藏还是订阅 | 改为 `继续浏览` |
| `email`、`telegram`、`wechat` | 英文标签增加理解成本 | 显示为 `邮箱`、`Telegram`、`微信` |
| `当前暂时没有开放岗位。` | “当前”和“暂时”重复 | `目前没有开放岗位。` |

招聘列表建议成稿：

`这里发布 Rebase 社区收到的公开岗位信息。岗位由招聘方提交，社区仅做基础格式整理；投递前请自行核实公司、岗位和联系方式。`

求职者看到的薪资、地点和远程状态必须可直接比较。币种、周期和办公方式应由招聘方写清楚，不要让用户猜 `$` 是哪种货币，也不要让前端替用户补全含义。

### 3.5 招聘方：我想知道能不能发布、发布后会怎样

当前只有 `提交职位` 一个动作，缺少用户最关心的三点：提交到哪里、社区会做什么、多久能看到。建议在按钮或旁边加一句：

`通过 GitHub Issue 提交岗位；社区会做基础格式整理，发布前请确认岗位、联系方式和截止日期准确。`

按钮改为 `提交岗位（打开 GitHub）`，如果按钮必须保持短，则在按钮下方补充说明，不把关键信息藏在 About 页。

### 3.6 活动参与者：我想知道活动是否值得去、现在能不能报名

| 当前文案 | 用户疑问 | 建议 |
| --- | --- | --- |
| `这里展示 Rebase 社区主办、参与和协助传播的活动。` | “协助传播”不代表谁负责活动 | `这里汇总 Rebase 主办、参与或社区提交的活动。` |
| `提交活动` | 点击后是否是报名？ | 保留按钮，但补充 `通过 GitHub Issue 提交活动` |
| `立即报名` | 需要明确是否会离开本站 | 保留，并在外链按钮使用 `↗`；必要时补 `打开报名页面` |
| `活动详情`、`查看详情` | 两个按钮指向相近页面 | 统一为 `查看活动详情` |
| `正在报名` | 清楚 | 保留；仅在确实有报名链接时出现 |
| `即将开始`、`即将举行`、`即将举办` | 状态太多 | 统一状态为 `正在报名`、`即将举行`、`往期活动` |
| `近期暂无公开活动` | “近期”没有范围 | `目前没有待发布的公开活动。` |
| `新的公开活动会在这里更新，也会同步进入活动 RSS 与历史归档。` | 未来承诺过多 | `新的公开活动会发布在这里，并同步到活动 RSS；历史活动见下方归档。` |
| `参与方式请查看正文中的活动说明，或以后续公告为准。` | 句子生硬，用户不知道哪条信息优先 | `参与方式请查看正文；如信息有变更，以活动方最新公告为准。` |
| `查看历史活动链接` | 可能被误认为还能报名 | `查看活动原链接（仅供归档参考）` |
| `继续关注` | 不清楚是关注还是订阅 | `继续浏览` |
| 日期和地点 | 用户可能不知道时间时区 | 在活动列表或详情加 `时间均为北京时间（UTC+8）` |

活动详情页的侧栏应按用户行动顺序排列：报名/活动链接 → 时间地点 → 活动说明 → 订阅活动 RSS/返回列表 → 相关活动。

### 3.7 潜在贡献者：我想知道自己能不能参与、从哪里开始

| 当前文案 | 用户感受 | 建议 |
| --- | --- | --- |
| `贡献者做什么？` 后面一大段任务罗列 | 信息太多，缺少最容易开始的动作 | 改为 `可以参与什么？`，先列 3–5 个具体例子 |
| `有热忱参与开源社区` | 任何社区都能这样说，无法判断是否适合自己 | `关注技术与社区，愿意投入时间完成具体协作。` |
| `实实在在的具体的事情` | 同义重复 | 删除重复表达 |
| `联系接引人 Harry、Frozen、Shooter` | “接引人”是内部词；固定姓名可能失效 | `通过协作文档或公开社区渠道联系我们。` 姓名只在确认仍有效时展示 |
| `加入我们` | 用户不知道加入什么、要付出什么 | `查看参与方式`；日报角色使用 `参与日报推荐` |
| `帮助日报保持长期内容密度` | 用户不懂“内容密度” | `帮助 GeekDaily 持续获得有价值的内容推荐。` |
| `持续参与后会在这里被记录和认可` | “认可”标准不明，像承诺 | `持续参与后，你的贡献会被记录在贡献者档案中。` |
| `X 位成员` | 容易让人以为有会员系统 | `X 位贡献者` |
| `历史贡献者` | 用户不知道是否还能联系这些人 | 加一句 `历史贡献者曾参与社区协作，当前不一定仍承担日常维护。` |

贡献者页三张卡建议直接使用：

- `可以参与什么？`：`推荐内容、更新日报、整理招聘、组织活动、撰写文章，以及维护网站和工具。`
- `适合怎样的人？`：`关注技术与社区，愿意投入时间完成具体协作。`
- `如何开始？`：`从一次具体协作开始，通过协作文档或公开社区渠道联系我们。`

### 3.8 About：我想确认社区是谁、如何联系、是否值得信任

About 不应只是首页定位语的重复。用户打开 About 通常想确认：社区做什么、有哪些栏目、如何参与、如何联系、捐赠是否安全。

当前空状态“关于页内容正在整理中。我们会很快补充 Rebase 的背景、理念与协作方式。”会让用户觉得网站尚未完成；“很快”也无法验证。建议改为：

`关于页内容暂未发布。你可以先浏览社区栏目、活动和贡献者介绍。`

如果 About 有正式内容，建议顺序为：

1. 一句话说明 Rebase 服务什么人、提供什么内容。
2. 栏目和项目：官方名称后补一句中文解释。
3. 如何参与：给出一个明确入口，而不是只列联系人姓名。
4. 联系方式：按“内容/活动/协作/社交”分组，避免一长串 URL。
5. 捐赠支持：说明用途、网络名称、地址核验方式和风险提示；在负责人确认前，不把捐赠写成无条件号召。

### 3.9 页头、页脚和社交入口

用户在页头需要的是“去哪里”，在页脚需要的是“还有哪些入口”。当前出现 `Who-Is-Hiring`、`Who is hiring`、`招聘`，以及 `Twitter`、`X / Twitter`、`关于Rebase`、`贡献者们` 等多种写法，会让用户怀疑这些是不是不同栏目。

建议导航统一为：

`首页｜极客日报｜招聘｜文章｜活动｜贡献者｜关于 Rebase`

页脚站点入口使用相同中文名称；项目外链才保留项目官方英文名。社交渠道统一显示 `X`，如需照顾旧用户，在 About 中首次写 `X（原 Twitter）`。

二维码文案可以更像用户操作提示：

- `关注 Rebase 微信公众号` / `打开微信，扫描二维码关注 Rebase 公众号。`
- `加入 Rebase QQ 群` / `打开 QQ，扫描二维码加入 Rebase QQ 群（群号：1001507060）。`

### 3.10 找不到、没有内容或加载失败时

用户遇到错误时不需要知道系统内部状态，只需要知道发生了什么、能否稍后再试、下一步去哪里。建议全站采用主动、短句模板：

| 场景 | 推荐标题 | 推荐说明 | 推荐动作 |
| --- | --- | --- | --- |
| 普通 404 | `找不到这个页面` | `链接可能已失效，或页面已经移动。` | `回到首页` |
| 文章 404 | `暂时找不到这篇文章` | `你可以返回文章列表，继续浏览已发布内容。` | `返回文章列表` |
| 活动 404 | `暂时找不到这个活动` | `你可以查看当前活动和历史活动归档。` | `返回活动列表` |
| 岗位 404 | `暂时找不到这个岗位` | `你可以浏览社区当前公开的岗位信息。` | `返回招聘列表` |
| GeekDaily 404 | `暂时找不到这期 GeekDaily` | `你可以返回列表，继续浏览最近和历史归档。` | `返回 GeekDaily 列表` |
| 搜索无结果 | `未找到匹配内容` | `换个关键词，或清空筛选条件后重试。` | `清空筛选` |
| 列表为空 | `目前还没有公开内容` | `有新内容时会发布在这里；你也可以订阅 RSS。` | `订阅 RSS` |
| 服务加载失败 | `暂时无法加载内容` | `请稍后刷新，或先返回列表继续浏览。` | `刷新` / `返回列表` |

应删除“这页内容暂时没有被找到”“这个招聘页面暂时没有被找到”等被动句式。

## 4. 面向用户的统一词汇

| 统一使用 | 不再使用 | 用户收益 |
| --- | --- | --- |
| `招聘` | `Who-Is-Hiring`（作为导航名）、`招聘板` | 一眼知道是岗位入口 |
| `贡献者` | `贡献者们`、`成员`（统计语境） | 不暗示存在会员体系 |
| `关于 Rebase` | `关于Rebase` | 中文排版自然 |
| `GeekDaily（极客日报）` | 首次只写 `GeekDaily` | 新用户马上知道栏目含义 |
| `GitHub` | `github`、`Github` | 品牌名正确 |
| `X` | `Twitter`、`X / Twitter` 混用 | 渠道名称一致 |
| `支持远程` / `需要到岗` / `混合办公` | `远程` / `线下优先` 混用 | 求职者能直接判断工作方式 |
| `前往投递` | `外部投递链接` | 行动结果明确 |
| `固定链接` | `链接规范` | 使用用户能理解的词 |
| `搜索` | `检索` | 与输入框和用户习惯一致 |
| `继续浏览` | `继续关注`、`继续追踪` | 不虚构收藏/关注能力 |

中文与英文品牌之间保留自然空格，如 `Rebase 社区`、`搜索 RSS`、`GitHub Issue`。中文句子使用中文标点；按钮优先使用“动作 + 结果”，不要使用后台字段名。

## 5. RSS 文案

RSS 用户通常不会打开官网确认上下文，因此 feed 名称必须独立、可识别。当前 `Rebase feed`、`GeekDaily feed`、`Rebase articles`、`Rebase events`、`Rebase hiring` 对中文用户不够直观。

建议统一为：

| 入口 | 标题 | 描述 |
| --- | --- | --- |
| 全站 RSS | `Rebase 社区 RSS` | `Rebase 社区最新的公开更新。` |
| GeekDaily RSS | `Rebase 极客日报 RSS` | `Rebase 极客日报的最新期目。` |
| 文章 RSS | `Rebase 文章 RSS` | `Rebase 社区最新文章。` |
| 活动 RSS | `Rebase 活动 RSS` | `Rebase 社区最新活动更新。` |
| 招聘 RSS | `Rebase 招聘 RSS` | `Rebase 社区最新招聘信息。` |

不要在 RSS 描述中使用“最稳定”“最常用”等比较性宣传语。RSS 条目本身只需准确呈现内容标题、摘要、时间和回到官网的链接。

## 6. 种子内容给用户带来的问题

以下内容虽然不是页面按钮，但会直接出现在用户面前，应该按同一套阅读标准维护：

- 岗位标题大量使用全小写英文，地点出现 `remote / shanghai friendly`、`remote / china time zone preferred` 等难以快速扫描的句子。
- 薪资写成 `$4,000 - $6,500 / month`，用户无法确认币种和周期。
- 活动标题使用英文城市和活动名，正文又混入 `builder`、`operator`、`archive nerd` 等标签；中文用户需要猜词义。
- 贡献者 headline 几乎全为英文，用户难以判断每个人具体负责什么。
- 文章卡片显示 `7 min read` 等英文阅读时长，和中文页面不一致。

建议给动态内容建立简单的用户可读规则：

1. 官方职位名可以保留英文，同时补充中文职位名或一句中文说明。
2. 地点写成 `远程｜上海优先`、`线上`、`深圳` 等可比较格式。
3. 薪资明确币种和周期，例如 `USD 4,000–6,500/月`。
4. 行业词首次出现时给中文解释，后续保持一种写法。
5. 阅读时长显示为 `约 7 分钟阅读`；标签如果展示给用户，也应提供中文显示名。

## 7. 建议落地顺序

### 第一优先级：让用户马上知道“这里是什么、能做什么”

- 重写首页首屏标题、摘要和两个 CTA。
- 导航和页脚统一为用户能理解的栏目名。
- 去掉或改写“每天更新、最稳定、最常用、很快补充”等不可验证承诺。

### 第二优先级：降低行动风险和理解成本

- 重写招聘真实性提示、过期岗位提示和投递按钮。
- 统一活动的报名、详情、回顾和历史链接文案。
- 给 About、贡献者页补上明确的参与入口。
- 统一 404、无结果、空列表和加载失败提示。

### 第三优先级：让长期阅读更舒服

- 统一中英文品牌、空格、大小写和状态词。
- 将 RSS 标题和描述改成中文。
- 按用户可读规则整理种子岗位、活动、贡献者和文章元数据。

## 8. 用户视角验收标准

文案更新后，找一位不了解项目的用户完成以下任务：

- 5 秒内说出 Rebase 是什么，而不是复述“非营利、业余时间”等背景词。
- 10 秒内找到 GeekDaily、文章、招聘和活动入口，并知道它们分别提供什么。
- 在岗位详情页能判断公司是否公开、岗位是否过期、如何投递、是否需要自行核实。
- 在活动详情页能判断活动状态、时间地点、是否有报名链接，以及外链会发生什么。
- 在贡献者页能说出从哪里开始参与，而不是只看到一串姓名或内部称呼。
- 在搜索无结果、页面不存在或内容加载失败时，能看到下一步动作。
- 订阅 RSS 后，仅凭 feed 标题就能分辨是全站、日报、文章、活动还是招聘。

本轮只更新审阅文档，不直接改动官网页面；最终改写应先确认社区定位、捐赠信息、固定联系人和招聘免责声明，再进入页面或后台发布流程。
